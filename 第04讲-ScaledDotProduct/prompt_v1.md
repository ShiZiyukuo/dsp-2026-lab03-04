# 提示词 v1（四要素版：输入 / 输出 / 约束 / 示例）

> 用途：让 AI 一次生成点积的 Python / C / Rust 三份实现 + 一个统一计时的
> benchmark 脚本。v1 是「初稿版」，只用四要素把需求说全，但计时口径写得弱
> （「跑一次计时」），因此留下隐患（见 v2 的单变量修改）。

---

## 提示词全文（直接复制给 AI 的部分）

你是熟悉 Python、C、Rust 三语言数值编程的工程师。请实现「float64 向量点积」的三语言版本，并写出统一计时脚本。

**【输入】**
1. 数据文件：`data/` 目录下已有成对的二进制文件，命名形如 `a_10000_f64.bin` / `b_10000_f64.bin`，规模 N = 10^4、10^5、10^6 各一对。
   - 格式：裸 IEEE-754 float64，**小端（little-endian）**，无文件头；元素个数 n = 文件字节数 / 8。
   - 三份实现必须读**同一份**二进制文件，不允许各自再生成随机数。
2. 点积定义：`dot(a, b) = a[0]*b[0] + a[1]*b[1] + ... + a[n-1]*b[n-1]`，按 `i = 0..n-1` 的**顺序**累加。

**【输出】**
1. `dot.py`：`def dot(a, b) -> float`；`dot.c`：`double dot(const double *a, const double *b, size_t n)`；`dot.rs`：`fn dot(a: &[f64], b: &[f64]) -> f64`。
2. 每个程序都要有一个「一次性模式」：命令行传入两个 bin 文件路径，载入、算一次点积，**打印校验和**，格式固定为 `N=<n> SUM=<17 位有效数字>`。
3. `benchmark.py`：调用三份实现，在 N = 10^4 / 10^5 / 10^6 上测量单次点积耗时，输出「规模 × 语言」耗时表，并给出 C、Rust 相对 Python 的加速倍数。
4. 每个文件开头写清编译/运行命令。

**【约束】**
1. **只用标准库**：Python 不得使用 numpy、numba、torch；C 不得链接 BLAS / MKL / OpenMP；Rust 不得引入 crate（只用 std）。三份实现都必须是「朴素循环」，不允许调用任何现成的点积/BLAS 函数。
2. C 必须用 `gcc -O2` 编译，Rust 必须用 `rustc -O`（release 优化）编译。
3. **循环内的结果必须被消费**：累加值要打印出来（校验和），不允许「算完就不要」。
4. 计时由 `benchmark.py` 用 `time.perf_counter()` 统一完成，只测点积本身，不包含文件读取。
5. 三语言结果要能相互核对，相对误差 ≤ 1e-9，且与 Python 基准一致。
6. 不要写死绝对路径；数据目录相对脚本位置解析。

**【示例】**
- 点积示例：`a = [1,2,3]`，`b = [4,5,6]` => `dot = 1*4 + 2*5 + 3*6 = 32`。
- 输出示例：`N=10000 SUM=60.163939325766698`
- 耗时表示例：

  | N | Python | C | Rust | C/Python | Rust/Python |
  |---|---|---|---|---|---|
  | 1e4 | ? | ? | ? | ? | ? |

**【要求】**
先讲思路（每种语言的性能关键在于什么），再给完整代码；代码可直接运行。

## v1 实际生成结果（原样保存要点）

AI 按 v1 给出的是「能跑通」的草稿，但出现了两类问题，都是靠人工复核才发现的：

1. **计时口径一开始不对**（真实发生、已实测复现）：脚本对每次测量只跑一次、直接 `perf_counter()` 包住
   `subprocess.run(...)`，把进程启动（Windows 上 10~30 ms）和 8~16 MB 文件读取都算进了 C / Rust 的耗时。
   现象（`logs/naive_whole_process.json` 实测）：N = 10^4 时 C 版「耗时」= 23.7 ms，而它的真实点积只有
   13.2 µs —— **虚高约 1800 倍**；C/Python 加速倍数从真实的 131× 被压到 4.8×，两个数量级的差距被抹平，
   结论方向被系统性带偏。
2. **C 版初稿的结果没被消费**（隐患，本机工具链下未触发）：初稿 `double s = dot(a,b,n);` 之后既没 `printf`
   也没累加到会输出的变量，gcc -O2 下这种写法常被整段删除。本机最终没有 gcc（WinLibs 下载中断），
   改用 MSVC cl /O2 复现时循环**没有**被删（`dumpbin /disasm` 仍见 mulsd/addsd），因此如实记录为
   「潜在隐患已排查、当前工具链未触发」，并保留「消费结果 + noinline」的防御写法，不编造「耗时趋近 0」的现象。

修错记录与最终 v2 见 `logs/` 与 `report`。
