# 提示词 v2（单变量迭代：只改「计时口径」这一句）

> **改动的唯一变量**：把 v1「【约束】4」里的
> 「计时由 `benchmark.py` 用 `time.perf_counter()` 统一完成，只测点积本身，不包含文件读取」
> 改为
> 「计时由 `benchmark.py` 用 `time.perf_counter()` 统一完成：编译型语言必须实现**应答式 worker 协议**——进程启动后先载入数据并打印 `READY`，之后每收到一条 `r <k>` 命令就重复算 k 次点积再回一行；计时只包住「写命令 → 读应答」，并**减去同进程内实测的管道往返基线 RTT**，再除以 k；预热 3 轮后正式计 10 轮取中位数，每种语言独立跑 5 次」。
>
> 其他一切（输入格式、接口签名、只用标准库、-O2 / release、示例、先讲思路再给代码）**保持 v1 原文不动**。

## 为什么只改这一句

v1 的「只测点积本身，不包含文件读取」在**口头上**是对的，但**没有给出可执行的协议**，
AI 只能自己发挥，于是它选了最省事的实现：`subprocess.run(...)` 整进程计时。
在 Windows 上进程启动要 10~30 ms，读 8~16 MB 文件又要几毫秒，而 N = 10^4 时 C 的点积只有
**13.2 µs**——启动开销是真实计算的约 1800 倍。这直接导致 v1 数据里 C 版 N=10^4 显示 23.7 ms、
C/Python 加速倍数只有 4.8×（真实 131×）的错误结论（见 `logs/naive_whole_process.json` 与
`logs/ablation.json` 的真实复现）。

同一句话里其实混了两个独立变量：
- (a) **计时是否包含 IO / 进程启动**（口径问题）
- (b) **测一轮还是多轮取中位数**（统计问题）

我选择先只改 (a)，因为 (a) 会**系统性地把结论方向搞反**（量级错误），
而 (b) 只影响精度（同一量级内的抖动）。把两个变量一起改，就无法归因到底是哪一句
修好了问题，所以 v2 只动 (a)：(b) 已经在 v1 的「预热 + 多轮」表述里，保持原样。

改完后 C / Rust 的计时口径与 Python **真正对齐**了：
三者都是「数据已在内存里、只计纯计算循环」，且都由外层 `perf_counter` 计量。

## 提示词 v2 全文（【约束】第 4 条为红色改动处）

你是熟悉 Python、C、Rust 三语言数值编程的工程师。请实现「float64 向量点积」的三语言版本，并写出统一计时脚本。

**【输入】**
1. 数据文件：`data/` 目录下已有成对的二进制文件，命名形如 `a_10000_f64.bin` / `b_10000_f64.bin`，规模 N = 10^4、10^5、10^6 各一对。
   - 格式：裸 IEEE-754 float64，**小端（little-endian）**，无文件头；元素个数 n = 文件字节数 / 8。
   - 三份实现必须读**同一份**二进制文件，不允许各自再生成随机数。
2. 点积定义：`dot(a, b) = a[0]*b[0] + a[1]*b[1] + ... + a[n-1]*b[n-1]`，按 `i = 0..n-1` 的**顺序**累加。

**【输出】**
1. `dot.py`：`def dot(a, b) -> float`；`dot.c`：`double dot(const double *a, const double *b, size_t n)`；`dot.rs`：`fn dot(a: &[f64], b: &[f64]) -> f64`。
2. 每个程序都要有一个「一次性模式」：命令行传入两个 bin 文件路径，载入、算一次点积，**打印校验和**，格式固定为 `N=<n> SUM=<17 位有效数字>`。
3. `benchmark.py`：调用三份实现，在 N = 10^4 / 10^5 / 10^6 上测量单次点积耗时，输出「规模 × 语言」耗时表，并给出 C、Rust 相对 Python 的加速倍数。
4. 每个文件开头写清编译/运行命令。

**【约束】**
1. **只用标准库**：Python 不得使用 numpy、numba、torch；C 不得链接 BLAS / MKL / OpenMP；Rust 不得引入 crate（只用 std）。三份实现都必须是「朴素循环」，不允许调用任何现成的点积/BLAS 函数。
2. C 必须用 `gcc -O2` 编译，Rust 必须用 `rustc -O`（release 优化）编译。
3. **循环内的结果必须被消费**：累加值要打印出来（校验和），不允许「算完就不要」。
4. **【本版唯一修改】** 计时由 `benchmark.py` 用 `time.perf_counter()` 统一完成：编译型语言必须实现**应答式 worker 协议**——进程启动后先载入数据并打印 `READY`，之后每收到一条 `r <k>` 命令就重复算 k 次点积再回一行；计时只包住「写命令 → 读应答」，并**减去同进程内实测的管道往返基线 RTT**，再除以 k；预热 3 轮后正式计 10 轮取中位数，每种语言独立跑 5 次。
5. 三语言结果要能相互核对，相对误差 ≤ 1e-9，且与 Python 基准一致。
6. 不要写死绝对路径；数据目录相对脚本位置解析。

**【示例】**
- 点积示例：`a = [1,2,3]`，`b = [4,5,6]` => `dot = 1*4 + 2*5 + 3*6 = 32`。
- 输出示例：`N=10000 SUM=60.163939325766698`
- 耗时表示例：

  | N | Python | C | Rust | C/Python | Rust/Python |
  |---|---|---|---|---|---|
  | 1e4 | ? | ? | ? | ? | ? |

**【要求】**
先讲思路（每种语言的性能关键在于什么），再给完整代码；代码可直接运行。

| 项目 | v1 整进程计时 | v2 应答式协议（减 RTT） |
|---|---|---|
| N=10^4 C 版 | 见 `logs/naive_whole_process.json`（毫秒级，被启动开销主导） | 微秒级，与 Python 拉出 2 个数量级以上差距 |
| 结论方向 | 「三语言差不多」 | 「C/Rust 比 Python 快两个数量级」 |
